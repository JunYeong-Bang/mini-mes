# 1단계 검증 기록

검증일: 2026-10-04 (Asia/Seoul). 기존 프로젝트 파일과 시스템 설정은 보존하고 새 `mini-mes` 폴더에서 수행했습니다. 새 프로젝트에 Git 저장소를 초기화했으며 커밋은 생성하지 않았습니다.

## 단계별 결과

| 단계 | 변경 내용 | 확인 결과 | 이해해야 할 개념 |
| --- | --- | --- | --- |
| 환경 확인 | 기존 파일·Java·MySQL 바이너리·Git·포트 확인 | Java 21, 기존 JAVA_HOME 17, MySQL 8.0.40 확인 | PATH의 java와 JAVA_HOME은 다른 JDK를 가리킬 수 있음 |
| 프로젝트 구성 | Boot 4.1.1, Maven Wrapper, MVC·JPA·Thymeleaf 구성 | Java 21 빌드 및 실행용 JAR 생성 성공 | 의존성·빌드 도구 버전 고정 |
| DB 구성 | 환경변수 접속, Flyway V1, JPA validate | 별도 실제 MySQL에서 마이그레이션·매핑 검증 성공 | 스키마 변경 이력과 엔티티 검증의 차이 |

## 실제 실행한 자동 검증

1. `.\scripts\maven.ps1 -DskipTests package`: Java 21 컴파일 및 실행용 JAR 패키징 성공
2. `.\scripts\maven.ps1 -B -ntp test`: H2에서 13개 통과, 별도 환경이 필요한 MySQL 테스트 12개 건너뜀
3. `.\scripts\verify-mysql.ps1`: 설치된 MySQL 8.0.40 실행 파일로 별도 로컬 서버를 시작해 전체 `verify` 수행

최종 전체 검증 결과:

```text
DevSampleDataTest: 1개, 실패 0, 오류 0
ItemFlowTest: 12개, 실패 0, 오류 0
MySqlItemFlowTest: 12개, 실패 0, 오류 0, 건너뛰기 0
총 25개 통과
BUILD SUCCESS
```

검증한 동작:

- 홈 리다이렉트, 목록·등록·수정 Thymeleaf 화면 렌더링, Bootstrap CSS 제공
- 등록 POST의 공백 제거·대문자 품번, 한국어 품목, 도면·설명 저장
- 공백 필수값, 너무 긴 값, 잘못된 품번 형식 거절과 저장 행 수 보존
- 등록 및 수정 품번 중복 처리, 소문자로 제출한 중복도 거절
- Service를 우회해 직접 중복 저장해도 DB UNIQUE가 차단
- 자기 품번을 유지한 수정, 비활성화 후 행 보존, version 증가
- 오래된 version 또는 누락된 version으로 수정하면 기존 데이터 보존
- 존재하지 않는 품목 조회·수정 시 404
- 입력된 HTML을 텍스트로 출력, 검색·페이지당 20건 처리
- Service 직접 호출에서도 입력 검증
- dev 예시 3개와 반복 실행 시 수정값·비활성 유지

같은 품목 흐름 테스트 12개를 H2와 실제 MySQL에서 각각 수행했습니다. H2의 MySQL 모드 결과만으로 MySQL 연결 성공을 판단하지 않았습니다. 두 DB에서 같은 V1 마이그레이션을 적용했고 JPA validate가 성공했습니다.

## 실제 HTTP와 재시작 검증

JUnit 밖에서도 패키징한 JAR을 실행해 Windows PowerShell의 HTTP 요청으로 확인했습니다.

- 검증용 DB: `127.0.0.1:13306/mini_mes_verify`
- 검증용 웹: `127.0.0.1:18080`
- dev 예시 3개가 검색 화면에 나타나는지 확인
- 실제 POST 등록 후 목록 확인, 같은 품번 재제출 시 한국어 중복 오류 확인
- 수정 화면의 version을 읽어 실제 POST 수정·비활성화
- SQL로 한국어 수정값과 active=0 저장 확인
- 앱을 종료한 뒤 같은 DB로 재실행해 전체 행 수와 수정값·비활성 유지 확인
- Flyway V1 성공 이력 확인, 재시작 로그에서 스키마 재적용 없음 확인

최종 스크립트 결과:

```text
PASS: 실제 MySQL 통합 테스트, HTTP 등록·중복·수정·비활성화,
      앱 재시작 후 데이터 보존, Flyway V1 이력
```

검증 스크립트의 초기 점검에서 Windows PowerShell의 UTF-8 스크립트 해석, native stderr 경고 처리, 앱 시작 직후 예시 데이터 준비 시점 문제를 발견했습니다. UTF-8 BOM, 종료 코드 기반 Maven 판정, 예시 데이터 준비 대기 조건을 반영한 뒤 위 전체 검증을 재실행해 통과했습니다.

실행용 JAR 내부 목록을 확인해 MySQL Connector 포함과 **H2 제외**를 확인했습니다. PowerShell 스크립트 구문 검사도 통과했습니다. Git dry-run과 ignore 확인에서 `.tools`, `.m2-local`, `target`이 관리 대상에서 제외되었습니다. 실제 접속 비밀번호는 저장소에 기록하지 않았습니다.

## 기존 DB와 검증 DB의 구분

기존 `127.0.0.1:3306`은 TCP 접속 응답만 확인했습니다. 기존 서버의 관리자·앱 계정 비밀번호가 없어 **로그인, mini_mes DB 존재, 개발용 앱 계정 연결은 확인하지 않았습니다.** 기존 DB에는 CREATE, ALTER, DELETE 등 어떤 SQL도 실행하지 않았습니다. 서비스 정보의 일부 조회는 접근 거부로 확인하지 못했습니다.

연결 성공을 확인한 것은 `--no-defaults`로 기존 설정을 읽지 않는 **별도 13306 서버**입니다. 검증 데이터 폴더는 `.tools/mysql-verify-<GUID>`로 매번 새로 만들었습니다. 이 서버는 기존 MySQL 서비스에 등록하거나 시스템 설정을 변경하지 않았습니다. 검증 후 스크립트가 실행한 앱과 DB 프로세스만 종료했고 파일은 보존했습니다. 기존 3306 서버를 개발에 사용하려면 README 순서로 DB와 앱 계정을 준비하고 환경변수를 지정해야 합니다.

## 실행하지 않은 검증과 현재 한계

- 사용자의 기존 3306 서버 계정 로그인과 실제 개발용 mini_mes DB 연결
- 브라우저에서 직접 보는 화면·모바일 레이아웃·키보드 사용성의 시각 점검
- 두 요청을 실제 동시에 보내는 부하·경합 테스트. 현재는 중복 DB 제약과 오래된 수정 version 거절을 개별 검증
- Linux/macOS Wrapper 실행: 이번 실행 환경은 Windows
- 로그인·권한·CSRF, 생산실적의 중복 제출·동시 수량 제한: 아직 기능 미구현
- 백업·복구, 외부 배포, 실제 공장 데이터·설비 연동: 이번 범위 밖

비실패 경고로 Flyway의 H2 2.4 지원 검증 범위 안내와 Mockito의 Java agent 관련 안내가 출력됐습니다. 실제 MySQL 검증과 테스트 성공에는 영향을 주지 않았습니다.

다음 작업은 품목 흐름을 직접 설명하고 등록·수정을 실행해 본 뒤 **설비 관리와 품목별 공정 순서**를 추가하는 것입니다. 설비 테이블은 새 V2 마이그레이션으로 만들며 현재 ERD는 그때 실제 구현 관계에 맞춰 확장합니다.
