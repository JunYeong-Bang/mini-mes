# 기존 MySQL 관리자 비밀번호를 모를 때 실행하기

기존 3306 서버의 비밀번호를 변경하지 않고, 설치된 MySQL 실행 파일로 Mini MES 전용 서버를 실행합니다. Windows 서비스 설치나 시스템 환경변수 변경은 필요 없습니다.

## 실행

PowerShell에서 프로젝트 폴더로 이동해 실행하세요.

```powershell
cd C:\Users\qkqhw\vsc\mini-mes
.\scripts\run-local.ps1
```

첫 실행에서는 **새 개발 DB 비밀번호**를 정하고 확인을 위해 두 번 입력합니다. 기존 MySQL root 비밀번호를 입력하는 절차가 아닙니다. 영문과 숫자를 포함한 6~72자이며, 기호는 가능하고 공백·한글은 제외합니다. 입력한 글자나 별표가 화면에 표시되지 않는 것은 정상입니다. 다음 실행에도 사용할 비밀번호이므로 기억하거나 개인 비밀번호 관리자에 보관하세요. 채팅에 보내거나 소스 파일에 적지 마세요.

스크립트가 DB·앱 계정을 준비하고 환경변수를 전달한 다음 앱을 실행합니다. 기본 JDK는 현재 PC에서 확인한 Zulu Java 21 경로를 명시합니다. README의 기존 DB 생성 SQL이나 환경변수 입력 명령은 이 실행 방식에서는 따로 수행할 필요가 없습니다.

앱 시작 후 **http://127.0.0.1:8080/items** 에 접속하세요. `Ctrl+C`로 앱을 중지하면 스크립트가 자신이 실행한 개발 DB도 종료합니다. 터미널 창을 강제로 닫기보다 `Ctrl+C`를 사용하세요.

다음에도 **같은 명령과 처음 정한 비밀번호**로 실행합니다. 이미 준비된 데이터 폴더에서는 초기화와 계정 생성을 다시 수행하지 않습니다. 등록·수정한 품목은 보존됩니다.

실행 정책이 차단하는 경우 해당 실행에만 적용하세요.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-local.ps1
```

## 연결 정보

| 구분 | 내용 |
| --- | --- |
| DB 주소 | `127.0.0.1:13307` |
| DB 이름 | `mini_mes` |
| 앱/Workbench 계정 | `mini_mes_app` |
| 비밀번호 | 첫 실행에서 직접 정한 새 개발 DB 비밀번호 |
| 데이터 위치 | `.tools/mysql-dev/data` (Git 제외) |
| 로그 위치 | `.tools/mysql-dev/run-<GUID>` (Git 제외) |

앱 실행 중 Workbench에서 **새 연결**을 만들어 위 주소와 계정으로 테이블을 확인할 수 있습니다. 기존 3306 연결 설정을 수정할 필요는 없습니다. 이 전용 서버의 root 계정에도 같은 개발 비밀번호를 지정하지만, 앱은 권한을 제한한 `mini_mes_app`으로 접속합니다. 비밀번호는 명령 인자나 설정 파일에 저장하지 않고 실행 중 메모리/자식 프로세스 환경변수로만 전달합니다. MySQL 자체 데이터에는 인증을 위한 해시가 저장됩니다.

이 연결은 로컬 루프백 개발용입니다. 인증에 필요한 공개키 조회를 허용하며 TLS를 사용하지 않습니다. 외부 서버에 사용하지 마세요. [MySQL 공식 데이터 디렉터리 초기화 설명](https://dev.mysql.com/doc/refman/8.0/en/data-directory-initialization.html)에 따른 초기화는 새 전용 폴더에서 최초 한 번만 수행합니다.

## 오류가 날 때

- **포트 사용 중**: 기존 프로세스를 종료하지 말고 `.\scripts\run-local.ps1 -DbPort 13308 -WebPort 8081`처럼 빈 포트를 지정하세요. 웹 주소도 지정한 포트로 접속합니다.
- **비밀번호가 다름**: 첫 실행에서 정한 개발 DB 비밀번호를 다시 입력하세요. 기존 root 비밀번호와는 별개입니다. 실패해도 데이터를 초기화하지 않습니다.
- **최초 준비가 중단됨**: 폴더를 삭제하거나 재초기화하지 않습니다. 안내된 로그를 확인하세요. 아직 개발 데이터를 넣기 전이라면 `-DataName mysql-dev-2`로 새 개발 폴더를 만들 수 있습니다. 이전 데이터는 자동으로 옮겨지지 않습니다.
- **실행 파일 없음**: `-MySqlHome`과 `-JdkHome`으로 설치 경로를 지정하세요.
- **같은 데이터 폴더가 이미 사용 중**: 이전 실행 터미널에서 `Ctrl+C`로 정상 종료한 후 재실행하세요. 다른 데이터 폴더의 서버를 이 스크립트에서 중지하지 않습니다.

## 검증

`-SmokeTest`는 패키징한 앱을 실행해 실제 MySQL 연결·마이그레이션·품목 HTTP 화면·dev 예시를 확인하고 종료합니다. JUnit 전체 검증을 대신하지 않습니다. 소스의 기존 `verify-mysql.ps1`은 별도 검증 DB를 사용하는 전체 자동 검증용입니다.

```powershell
.\scripts\run-local.ps1 -SmokeTest
```

2026-10-07 (Asia/Seoul) 실제 검증 결과:

- Windows PowerShell 5.1에서 새 전용 폴더 `mysql-dev-check-53516fbaf9064698bb6eedd1f991876e`, DB 13317, 웹 18087로 검증했습니다. 사용자가 비밀번호를 정할 기본 `.tools/mysql-dev` 폴더는 만들지 않았습니다.
- 첫 초기화, 앱 계정 접속, Java 21 패키징, 앱 HTTP 200, dev 품목 3개, Flyway V1 이력을 확인했습니다.
- 같은 폴더와 비밀번호로 재실행해 품목 3개와 V1 이력이 유지되는 것을 확인했습니다.
- 다른 비밀번호는 거절됐고, 원래 비밀번호로 다시 실행해 같은 데이터가 유지됐습니다. 이 오류 경로에서는 직접 시작한 전용 프로세스를 종료하고 다음 시작 시 MySQL의 복구를 거칩니다.
- 종료 후 검증 DB·웹 포트가 반환됐고, 환경변수가 원래 값으로 복원됐습니다. 검증 데이터 파일은 삭제하지 않았습니다.
- 사용 중인 포트는 비밀번호 입력과 DB 초기화 전에 거절했습니다. PowerShell 구문 검사와 데이터 폴더의 Git 제외도 확인했습니다.
- 최초 점검에서 Windows PowerShell의 종료 코드 조회와 .NET Framework 입력 인코딩 차이, MySQL의 자식 모니터 프로세스 문제를 발견했습니다. 핸들 확보, UTF-8 바이트 입력, `--no-monitor`로 수정한 뒤 위 검증을 완료했습니다.

이번 검증에서는 패키징 시 `-DskipTests`를 사용했습니다. JUnit 전체 검증은 재실행하지 않았으며 기존 결과는 [verification.md](verification.md)에 있습니다. 직접 비밀번호를 입력하는 사용자 터미널 UI, 일반 실행 중 키보드 `Ctrl+C` 동작, Workbench 새 연결의 화면 조작은 자동 검증하지 않았습니다. 기존 3306 관리자 로그인도 여전히 확인되지 않았습니다.
